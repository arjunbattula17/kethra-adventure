# Learnings

## Inspection — 2026-09-06
- `tools/collision-check.mjs`'s walk-only flood fill is a reliable way to catch unreachable interaction targets, but it doesn't model jumping — a target flagged unreachable still needs a quick manual/arithmetic check against `PlayerController`'s `JUMP_SPEED`/`GRAVITY` (max jump height = `JUMP_SPEED² / (2·|GRAVITY|)`) before concluding it's a real bug rather than an intended jump-across gap.
- `KethraScene.buildTerraces()` places `landing`/`plaza`/`westTerrace`/`eastTerrace`/`chamberApproach` as separate `makeTerrace()` boxes with no connecting geometry between several of them — three multi-meter voids (plaza↔westTerrace, plaza↔eastTerrace, plaza↔chamberApproach) have existed since before this session and were never caught because `collision-check.mjs` didn't support the Kethra scene until this session added it. Worth checking newly-instrumented scenes' *existing* content, not just the lines touched in the current diff.
- TypeScript `private` is compile-time only — `tools/collision-check.mjs` calls `sc.player.sampleFloorHeight(...)` (declared `private` in `PlayerController.ts`) from plain JS at runtime, which works but isn't type-checked. Fine for a diagnostic tool; would be worth a comment noting it's a deliberate escape hatch. (Later fixed properly: `sampleFloorHeight` was made a documented public method.)

## Inspection — 2026-09-06 (follow-up, performance + regression pass)
- **`THREE.Cache.enabled = true` combined with GLTFLoader's `ImageBitmapLoader` corrupts textures when multiple glTF files sharing a texture URL load concurrently.** Verified live (A/B test: 34 broken textures in the ship interior kit, 75 in the Kethra nature kit, both dropping to 0 with `Cache.enabled = false`). The network layer is NOT at fault — each texture URL is fetched exactly once, with a 200 and correct content-type, confirmed via request/response logging. Traced into three.js's own `ImageBitmapLoader`/`GLTFLoader.loadImageSource` — `Cache.add('image-bitmap:'+url, promise)` registers the in-flight promise so concurrent loaders await the same fetch, which looks correct in isolation, but multiple concurrent `GLTFLoader.parse()` calls (each with its own `ImageBitmapLoader` instance, per this project's kit.ts loading one glTF per kit piece) sharing that cached entry end up with `Texture.image === undefined` for a large fraction of them. Did not pin the exact defect line in three.js; the cause-and-effect of the flag is conclusive. **Do not enable `THREE.Cache` in a codebase that loads many small glTF files sharing a texture folder via `Promise.all`, without first testing for exactly this** — the dedup benefit it's meant to provide should instead be implemented as an app-level per-URL promise cache (e.g. a `Map<url, Promise<Texture>>` in the kit loader itself), which doesn't have this failure mode.
- Test tooling that identifies a scene via `scene.constructor.name === 'SomeSceneClass'` (as `collision-check.mjs`, `movement-check.mjs`, `interaction-check.mjs` all do) works fine against `vite dev` but silently hangs (90s timeout, no useful error message) against a minified `vite build` + `vite preview`, because minifiers rename classes (observed mangled to `"TS"`). Worth using a stable `readonly kind = 'ShipInteriorScene'` string property instead of `constructor.name` if these tools should ever validate what actually ships.
- When investigating "why is this laggy," always test against BOTH `npm run dev` and a production `vite build` + `vite preview` — the two can have wildly different bottlenecks (dev pays a module-fetch-waterfall tax that prod doesn't; both pay the same shader-compile-count cost), and a fix validated only in one mode can look like it solved nothing in the other, or vice versa.

## Opening tutorial — 2026-09-06
- **Headless Chromium throttles rAF and `setTimeout` in a page nothing is interacting with, and it is severe: measured one animation frame every ~4 seconds, and a 2.45 s `setTimeout` chain taking 61 s of wall clock.** Anything in `tools/` that waits on the game's own timers or on frame-driven state needs `chromium.launch({ args: ['--use-gl=angle', '--enable-unsafe-swiftshader', '--disable-background-timer-throttling', '--disable-renderer-backgrounding', '--disable-backgrounding-occluded-windows'] })`. The GL flags matter as much as the throttling ones — with them the render loop tracked wall clock 1:1 (5.11 sim seconds per 5 wall seconds at the `low` quality tier). A `page.evaluate()` poll also wakes the page, which is why a harness that polls looks fast and one that only calls `waitForSelector` looks hung. Note that software rasterisation then makes the ship interior take ~20 s to boot where real hardware takes ~2 s, so timeouts have to be generous *and* waits should poll for conditions rather than sleep fixed intervals.
- `THREE.Raycaster` checks neither `object.visible` nor `material.visible` (verified in `node_modules/three/src/core/Raycaster.js` and `objects/Mesh.js` — `intersect()` only tests layers, and `Mesh.raycast` only bails on `material === undefined`). An invisible-material proxy mesh is therefore hit-testable while costing no draw call, which is how the console's monitor bank became its own interaction target without pulling ~45 meshes out of the static batch. `buildInteriorColliders` also skips `MeshBasicMaterial`, so such a proxy contributes no collider either.
- `tools/test-save-load.mjs` fails on its second `page.goto(baseUrl, { waitUntil: 'load' })` with a 30 s timeout. Confirmed pre-existing (reproduced with `git stash push -- src`), same throttling family as above — it needs the launch flags and a longer timeout, not a code fix.
- Three defects in the opening tutorial, all of the same shape — **state or layout that is scoped wider than the thing reading it**:
  - `InteractionSystem`'s proximity fallback compared camera-to-origin distance and nothing else, so standing at the console facing the opposite wall raised "Access Navigation Console". The fix tests facing on the **horizontal plane only**: the fallback exists precisely because the player is looking over or under a low target, so letting pitch veto it would break the case it is there for. `tools/interaction-check.mjs` now re-checks every obtained target from the same spot turned 180°.
  - `TutorialSequence.openedCharacterSheet` was latched by a `window` keydown listener registered in `start()`, with no per-step window. The HUD advertises `TAB — Character` from the first frame, so any early Tab pre-satisfied step 3 and it self-completed on entry. Gates fed by long-lived listeners need clearing in the step's own `enter()`, the way step 1 clears `lookAmount`.
  - The waypoint's NDC edge-clamp band (`EDGE_Y = 0.8` → 90% of viewport height) falls **inside** the instruction card at every viewport size, so a target directly behind the player parked the arrow on the card's own sentence. Screen-space markers need to be clamped against the other HUD elements, not just against the viewport.

## Galaxy reveal polish + puzzle removal — 2026-09-09
- **`window.__DEBUG__` is exposed before `flow.start()`'s boot `setScene` resolves.** A harness that calls `flow.transitionToGalaxyReveal()` as soon as `__DEBUG__.gameState` exists races the still-in-flight boot `setScene(interior)`: under software rendering the boot's `compileAsync` can run 20-30s, land *after* the reveal's own setScene, and silently clobber the reveal (current scene flips back to `ShipInteriorScene`, `engine.start()` hasn't even run yet so scene clocks sit at 0). Every tool that drives the flow must first wait for `engine.getCurrentScene()` to be non-null. This is the async-writes-serialize failure shape: two unserialized async `setScene` calls, last-writer-wins.
- **Playwright's default `waitForFunction` polling is rAF-based and starves during boot.** While the main thread runs long synchronous tasks (PMREM build, kit parsing) — and 4x CDP throttle stretches them — an rAF-polled wait can blow a 45s timeout while the page is making progress. Pass `{ polling: <ms> }` for any wait that spans scene construction.
- **`frame-trace.mjs`'s `BASE_URL` is concatenated with `?query` directly** — a value without the trailing slash (`.../kethra-adventure`) produces `/kethra-adventure?...`, the server 404s, and the tool times out looking like a boot hang. Use `BASE_URL=http://host:port/kethra-adventure/`.
- **The freighter GLB's `mat13` ("running lights") also skins the four big aft hexagonal panels.** Any emissive intensity above ~0.6 turns them into huge flat cream discs that dominate every stern shot — found by hiding materials one at a time in a live scene (`o.material.visible = false` per material name), which beats guessing from the material's palette role.

## Performance pass — 2026-09-09
- **The ship interior spent ~46% of its draw calls (~1,100 of ~2,470) re-rendering a pixel-identical shadow map every frame.** Decomposed by toggling passes live: base scene 1,231 calls, GTAO +1,224 (inherent — it re-renders the scene for depth/normals from the moving camera), shadows +1,136, bloom +13. Only one light casts shadows and nothing that casts one ever moves (the two animated transforms are castShadow-false screen-sweep quads; light animation is intensity-only, which the depth map doesn't see), so `renderer.shadowMap.autoUpdate = false` + one `needsUpdate` per scene entry is free. Verified pixel-identical by hashing `gl.readPixels` of the same paused frame under frozen vs live shadows. Result on the 4x-throttled prod trace: ship-hero p50 46.3→36.1ms, ship-walk p50 37.2→26.3ms and drop-below-30fps 87%→14%.
- **`renderer.info.render` auto-resets at the end of every `render()` call**, and EffectComposer issues several per frame — reading it from outside the loop shows a near-zero remnant (observed "1 draw call"). To get true per-frame totals: `info.autoReset = false`, `info.reset()` in one rAF, read in the next, restore.
- **Kethra is raster-bound, not main-thread-bound** (79% main-thread idle at 500 calls / 1.24M tris under SwiftShader), and the interior's main-thread cost is almost entirely three.js draw-submission internals (uniform setValue/bind machinery) — GC never appeared in any top-30 profile, so allocation-churn micro-fixes here have no evidence behind them. `tools/perf-profile.mjs` (CDP sampling profiler + per-frame renderer stats) is the tool that established all of this.

## Low-end pass — 2026-09-10
- **SettingsPanel.init() was silencing the entire adaptive quality system for every player.** It applied DEFAULT settings through `setManualQualityTier()` on every boot, which sets `manualOverride` — so the core-count hardware guess and the runtime downgrade monitor never ran for anyone: a 2-core machine booted forced-high (AO + bloom + shadows) and stayed there. Every "bad-laptop" frame-trace ever taken ran in that misconfigured state. The distinction that matters: *saved* settings are a player choice; *defaults* are not — only the former may claim manual override.
- **Texture VRAM must be audited at the Source level, not the Texture level.** three r185 shares one GL texture across all Texture clones with the same `source` + sampler cache key (WebGLTextures.js `getTextureCacheKey`), so summing per Texture-uuid triple-counted the kit maps (~900MB "measured", ~344MB real). The existing textureCache.ts dedup works.
- The interior's remaining ~170MB of texture memory is *procedural canvas textures* (1536-2048px canvases from *Textures.ts modules), not kit files — future low-tier candidate if VRAM pressure ever shows again.
- Governor design that works with the existing one-directional philosophy: below the low tier, the same sustained-p95 evidence steps an internal render scale 1 -> 0.85 -> 0.7 (never back up mid-session; manual tier choice resets it). Kethra under the 4x/2-core profile: p50 43.3 -> 16.6ms, 0% frames below 30fps.

## Loading pass — 2026-09-10
- **compileAsync is not "first-draw ready".** It links programs (KHR_parallel_shader_compile polling works — the extension IS present under ANGLE/SwiftShader), but drivers defer per-program draw specialization and every texture upload to first *use*. Measured on the software-rendered prod boot: scene:init 2.0s + scene:compile 15.6s, then a ~40s single-task stall in the FIRST VISIBLE FRAME (93 programs, ~300 texture sources) — i.e. right after the loading overlay hid, and equally right after every scene-transition fade lifted. Fix: one `postFx.render()` warm-up inside Engine.setScene while the overlay/fade still covers the screen; first two post-ready frames dropped from that stall to 36ms. Total work unchanged — it just happens where the loading UI is honest about it.
- Boot network is a non-issue: 34 requests / 6.2MB total to a playable interior. Don't spend effort consolidating kit fetches.
- `page.waitForFunction(fn, { timeout })` passes the options object as the page function's ARGUMENT and silently keeps the 30s default timeout — the third-parameter position is the real one. This bit test-tutorial-flow.mjs the moment the warm-up frame made boot a single long task. Same family as the rAF-polling starvation note above; both waits now use `undefined, { timeout, polling }`.

## Loading/lag diagnosis — 2026-09-13
- **CORRECTION to every earlier "under SwiftShader" caveat: the harness has been using the real GPU all along.** `--enable-unsafe-swiftshader` only *permits* software rendering; headless Chromium on this machine reports `ANGLE (NVIDIA, NVIDIA GeForce RTX 4060 ... D3D11)`. All capture/trace numbers were real-hardware numbers, and the game is vsync-locked at 60fps in every tier here — even forced High at deviceScaleFactor 2.
- **"Loading is slow" is ANGLE/D3D shader compilation, gated by Chrome's shader disk cache.** Cold cache: init 1.8s + compile 17.4s + warmup 48.9s ≈ 68s to the tutorial on an RTX 4060. Warm cache: 12s total (compile 8.5s, warmup 1.4s). Playwright's fresh profiles are always cold, which is why every harness boot looked catastrophic. The ~45s cold warmup persists even at the LOW tier (no shadows/AO/bloom/MSAA), so it is the scene's own ~93 programs being genuinely compiled at first *draw* — on ANGLE, KHR_parallel_shader_compile's completion status does not mean first use is free, and compileAsync cannot force it. The only real lever left is reducing the program count (93 programs from 394 materials — feature-flag normalization), recorded as future work.
- **"It's laggy/slow" was substantially environmental:** the user-facing game was being played through a vite DEV server running since Sep 6 (unminified, 106 requests vs 38, checkShaderErrors on — which doubles boot blocking), and nine orphaned node/vite servers from killed background sessions were squatting ports 4173-4179/5181/5199. Killed the orphans; play the built version.
- Playwright `launchPersistentContext` with a reused user-data-dir is how you A/B Chrome's shader cache; `rmSync` the dir for a guaranteed-cold run.
